# Native Google sign-in for Android DEV

This contract is limited to `supermeapp-dev-android` on the DEV auth server. It does not change website Google sign-in or production OAuth clients.

## Native button action

The hosted Android login page renders a Google button that links to the exact URI `superme://oauth/dev/google`. Android must intercept this action and launch the native Google SDK. The URI contains no credentials or tokens. Return the Google ID token to the application in memory and send it to the backend over HTTPS in the JSON request below. Do not add a JavaScript bridge or put a Google ID token in a URI.

## Google client claims

- Android package: `com.superme.app`
- Google ID-token `aud`: `124581866222-gblqv0k2a75uo4183ahl0u8336nbcsku.apps.googleusercontent.com`
- Expected `azp`: `124581866222-kgg99hqv2fcmac8rfra4mslsuqcb40kq.apps.googleusercontent.com`
- Android signing SHA-1: `546a1c3bbea4de454ab538afa5e2e25cd512fc5c`
- Android signing SHA-256: `67243057a7c5d32387fd805fac14fc368e6ef10d141f9ac4462f88e0d69f6aa2`

The server checks signature through Google's configured JWKS decoder, accepted issuer, expiration/not-before, the exact single audience, authorized party, Google nonce, and verified email. It never trusts an email by itself. The actual `aud`/`azp` values must still be confirmed with a native SDK token during device integration.

## Hosted Turnstile, then native Google sign-in

The new hosted-check flow uses the existing auth-hosted widget and DEV secret. The CAPTCHA response stays in a same-origin HTTPS form post; it is never returned to the app or placed in a callback URL. The older `/v1/auth/android-dev/google` request contract remains available but still requires `turnstileToken`; Android should use the hosted flow below so it does not need to extract a token from the hosted page.

### 1. Start a security-check transaction

Android generates and temporarily retains a PKCE verifier, S256 challenge, Google nonce, OIDC nonce, and random `state`. It sends the public parameters in the request body:

`POST https://auth.supermeapp.com/v1/auth/android-dev/google/turnstile`

```json
{
  "clientId": "supermeapp-dev-android",
  "redirectUri": "superme://oauth/dev/callback",
  "codeChallenge": "<base64url(SHA-256(code_verifier))>",
  "codeChallengeMethod": "S256",
  "googleNonce": "<nonce to send to the native Google SDK>",
  "oidcNonce": "<nonce to validate in the eventual SuperMe ID token>",
  "state": "<random state generated by Android>"
}
```

Response (`200`, `Cache-Control: no-store`):

```json
{
  "transactionId": "<opaque random transaction id>",
  "securityCheckUrl": "https://auth.supermeapp.com/android-dev/google-security?transaction=<opaque-id>",
  "expires_in": 300
}
```

The transaction expires after 5 minutes and is bound server-side to the Android client, registered callback, PKCE challenge, both nonces, and state. The ID is opaque and is not a CAPTCHA or authentication token. Use the Android native HTTP client for this initiation request if the app origin is not in the browser CORS allowlist.

### 2. Open the hosted security page

Open `securityCheckUrl` in a browser context that can return app links to Android. The page served by `auth.supermeapp.com` renders the configured Turnstile widget. After the user completes it, the page posts the response to the same auth host, and the backend verifies it with Cloudflare using the existing secret.

On success the backend returns a redirect to the registered callback, for example:

```text
superme://oauth/dev/callback?android_google_ticket=<opaque-one-time-ticket>&state=<original-state>
```

The callback contains only the short-lived handoff ticket and the original state. It contains no CAPTCHA response, Google ID token, access token, refresh token, or authorization code. Android must compare `state` with the retained value before accepting the callback. The handoff ticket expires after 5 minutes and can be redeemed once. Closing/cancelling the browser before the callback means no ticket is issued to the app; Android may call the cancellation endpoint below and start over later.

Optional cancellation:

`POST https://auth.supermeapp.com/v1/auth/android-dev/google/turnstile/cancel`

```json
{"transactionId":"<transactionId from initiation>"}
```

Response: `200 {"cancelled":true}` (false means it was already expired, cancelled, or completed).

### 3. Start native Google and redeem the ticket

After validating `state`, Android starts the native Google SDK with the retained Google nonce. It sends the resulting Google ID token and the handoff ticket in an HTTPS JSON body:

`POST https://auth.supermeapp.com/v1/auth/android-dev/google/exchange`

```json
{
  "clientId": "supermeapp-dev-android",
  "handoffTicket": "<ticket from the app callback>",
  "googleIdToken": "<Google ID token>"
}
```

The backend consumes the ticket atomically before verifying Google, checks the Google token signature, issuer, audience, authorized party, expiry, and the ticket-bound Google nonce, then reuses the existing DEV account lookup and active-account checks. A failed or repeated redemption requires a new security transaction and Google sign-in. Success is `200`, `Cache-Control: no-store`:

```json
{"code":"<single-use authorization code>","expires_in":60}
```

The code is bound to `supermeapp-dev-android`, the registered callback, the ticket’s PKCE S256 challenge, and OIDC nonce. Exchange it at `/oauth2/token` with `grant_type=authorization_code`, `client_id=supermeapp-dev-android`, the registered redirect URI, returned `code`, and the saved `code_verifier`; no client secret is used. The issued ID token contains the original OIDC nonce. Access/refresh/ID tokens are returned only from the HTTPS token endpoint, never in a callback URL.

### Errors and retry behavior

| HTTP | `error` | FE handling |
| --- | --- | --- |
| 400 | `invalid_client`, `invalid_redirect_uri`, `invalid_pkce`, `invalid_request` | Fix configuration/request; start a new attempt. |
| 401 | `invalid_handoff` | Ticket expired or replayed; start a new security check and Google sign-in. |
| 401 | `captcha_failed` | The hosted check was not accepted; complete a fresh check. |
| 401 | `invalid_google_credential` | Google credential was rejected; start again with a fresh native Google token. |
| 409 | `registration_required` | Continue through existing DEV onboarding, then start sign-in again. |
| 409 | `google_token_replayed` | Start again with fresh Google and OIDC nonces. |
| 429 | `too_many_requests` | Back off before retrying. |
| 503 | `bot_protection_unavailable`, `client_not_ready`, `google_client_not_ready` | Preserve app state and retry later after configuration is restored. |

The hosted transaction and ticket are stored as hashes in the auth database, expire after 5 minutes, and are single-use through atomic database updates, including across server instances. No Google token or CAPTCHA response is written to application logs or callback URLs.

## Exchange code for tokens

`POST https://auth.supermeapp.com/oauth2/token`, form URL encoded, no client secret:

```text
grant_type=authorization_code
&client_id=supermeapp-dev-android
&redirect_uri=superme%3A%2F%2Foauth%2Fdev%2Fcallback
&code=<returned-code>
&code_verifier=<original-verifier>
```

The standard token response contains `access_token`, `refresh_token`, `id_token`, `token_type`, and `expires_in`. The ID token's `nonce` is the exact `oidcNonce` sent in the JSON request. Android client policy remains 15-minute access tokens and 7-day rotating refresh tokens, with refresh-token reuse detection enabled. Persist the returned token set atomically in Android's existing Keystore-backed storage.

## Existing users and onboarding

The endpoint reuses the existing Google account lookup/linking and active-account checks, restricted explicitly to the DEV user repository. A valid Google identity without an existing SuperMe account receives `409 registration_required`, with the verified identity fields that can prefill onboarding and required fields (`gender`, `dateOfBirth`, `relationship`). No OAuth code or tokens are issued for an unregistered account. Continue through the existing DEV onboarding/registration flow; after the account is created, request native Google sign-in again. A deleted, disabled, or otherwise unusable account receives `401 unusable_account`.

## Errors

Errors are JSON `{ "error": "...", "error_description": "..." }`, with `Cache-Control: no-store`:

| HTTP | `error` | Meaning |
| --- | --- | --- |
| 400 | `invalid_request`, `invalid_client`, `invalid_redirect_uri`, `invalid_pkce` | Fix request/configuration and start a new attempt. |
| 401 | `invalid_google_credential` | Google token validation failed; obtain a fresh native Google credential. |
| 401 | `unusable_account` | Account is disabled/deleted or cannot authenticate. |
| 409 | `registration_required` | Finish existing DEV onboarding, then start sign-in again. |
| 409 | `google_token_replayed` | Google nonce was previously used; start a new Google sign-in. |
| 429 | `too_many_requests` | Wait according to rate limit, then retry with a fresh sign-in attempt. |
| 503 | `client_not_ready`, `google_client_not_ready` | DEV server configuration is incomplete; do not retry in a tight loop. |

## Logout

This addition does not change the existing Android logout/revocation endpoints or browser-session behavior. It does not send login credentials or Google, access, or refresh tokens in a URL or log. Continue using the already integrated DEV logout contract and clear the Keystore-backed token set in the app.

## Verification status

Focused automated tests cover hashed transaction storage, expiry, one-use redemption, the hosted Turnstile success/failure redirect behavior, code issuance with the bound PKCE challenge and OIDC nonce, and the pre-existing direct Google endpoint behavior. The full auth-server suite could not complete in this sandbox because it blocks Tomcat binding an ephemeral test port; the DEV CI pipeline must run the full suite before deployment. A real Google native ID token, device login, wrong-audience/expired token against Google's live keys, and deployed DEV end-to-end test still require the FE/device test run.
