# Sign in with Apple release checklist

## Values confirmed in this repository

| Setting | Value | Location |
| --- | --- | --- |
| iOS bundle ID / native Apple audience | `com.supermeapp.app` | Xcode project, Firebase iOS plist, production environment |
| Apple Developer Team ID | `9QZU552289` | Xcode signing settings and the latest archive summary |
| Sign in with Apple entitlement | `Default` | `ios/App/App/App.entitlements` |
| Native redirect URL | Not used | Native `AuthenticationServices` returns directly to the app |
| Custom app URL scheme | `superme` | `ios/App/App/Info.plist` |

The Sign in with Apple capability is enabled in both the entitlement and Xcode
target metadata. The latest checked archive summary also contains
`com.apple.developer.applesignin`.

## Apple Developer portal checks required before archiving

These values cannot be verified from source control and must be checked by an
Account Holder or Admin:

1. Open Certificates, Identifiers & Profiles and select App ID
   `com.supermeapp.app`.
2. Confirm Sign in with Apple is enabled and configured as the primary App ID,
   or intentionally grouped with the correct existing primary App ID.
3. Regenerate the distribution provisioning profile after any capability
   change.
4. Confirm the App Store Connect app uses bundle ID `com.supermeapp.app`.
5. A Services ID and return URL are required only for a separate web Sign in
   with Apple flow. They are not used by this native iOS flow.
6. Keep the Apple private key (`.p8`), Key ID and server client secret only on
   the backend. Never add them to this mobile repository.

## Backend verification contract

`POST /v1/auth/oauth2/mobile-login` now receives the following Apple fields:

```json
{
  "provider": "apple",
  "providerId": "Apple stable user identifier",
  "email": "Apple verified or private-relay email when available",
  "name": "Only supplied by Apple during the first authorization",
  "idToken": "Apple identity JWT",
  "identityToken": "Apple identity JWT",
  "authorizationCode": "Single-use Apple authorization code",
  "rawNonce": "Nonce generated by the app before authorization",
  "clientId": "com.supermeapp.app"
}
```

The backend must:

- fetch Apple public keys and verify the JWT signature and `kid`;
- require issuer `https://appleid.apple.com`;
- require audience `com.supermeapp.app`;
- validate token expiry and the nonce claim against `SHA-256(rawNonce)`;
- use the verified `sub` claim as the stable account identifier;
- verify/exchange the single-use authorization code with Apple when required;
- save first-login name/email and reuse those values for returning users;
- never identify or merge accounts using an unverified client-supplied email;
- return the saved user, token and `onboardingStep`;
- reject replayed, expired, wrong-audience or invalid-signature credentials.

## Development mock (never active in production)

The production environment hard-disables Apple mock authorization. In a local
development build, enable it explicitly in the browser console:

```js
localStorage.setItem('superme_apple_mock_enabled', 'true');
localStorage.setItem('superme_apple_mock_scenario', 'first-login');
location.reload();
```

Supported scenarios:

- `first-login`
- `returning-login`
- `cancelled`
- `error`

Disable it with:

```js
localStorage.removeItem('superme_apple_mock_enabled');
localStorage.removeItem('superme_apple_mock_scenario');
location.reload();
```

Mock JWTs are deliberately unsigned. The app never sends them to Firebase or
the configured backend; it shows a confirmation and opens the client
onboarding UI only. The mock exists to test client UI, error handling and
first/returning credential normalization without an Apple device. Final
onboarding submission must be tested against a local/staging backend with real
Apple credentials. Automated unit tests cover the credential cases.

## Pre-submission test matrix

- First authorization with "Share My Email"
- First authorization with "Hide My Email"
- Returning authorization (Apple omits the name)
- Completed user routes to Home
- Incomplete user routes from backend `onboardingStep`
- User cancellation produces no error toast
- Network/server error shows a useful message and preserves no partial session
- Wrong audience, expired token and nonce mismatch are rejected
- Revoke SuperMe under Apple ID Sign-In settings, then authorize again
- Archive uses a distribution profile containing the Apple Sign-In entitlement
