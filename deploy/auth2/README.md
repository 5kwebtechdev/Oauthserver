# Auth2.0 automatic deployment

Place `.github/workflows/auth2-deploy.yml` at the **GitHub repository root** on
branch `main` or `Auth2.0`. If BE is a subdirectory in GitHub, move only the workflow into
the repository root's `.github/workflows/`; keep `deploy/auth2` beside the backend
parent `pom.xml`. The workflow locates the backend automatically. This local
workspace is not a normal standalone Git checkout, so no commit or push was made.

The workflow uses your existing repository secrets `SERVER_HOST`, `SERVER_USER`,
and `SERVER_SSH_KEY`. They must point to `187.127.142.16` and an account that is
root or has passwordless sudo. SSH credentials are never stored in this file.
As in your existing workflow, SSH host keys are obtained with `ssh-keyscan`.

## One-time server setup

At the server's root prompt, ensure Java 21, curl, and OpenSSL are installed:

```bash
apt update
apt install openjdk-21-jre-headless curl openssl iproute2
```

Your existing `/root/privateKey.pem` and `/root/publicKey.pem` must be matching
RSA keys, with headers `BEGIN PRIVATE KEY` and `BEGIN PUBLIC KEY` respectively.
No keys are copied from GitHub or generated by the workflow.

Upload the example environment files from your local BE folder:

```bash
ssh root@187.127.142.16 'mkdir -p /root/Auth2.0'
scp deploy/auth2/auth.env.example root@187.127.142.16:/root/Auth2.0/auth.env.example
scp deploy/auth2/resource.env.example root@187.127.142.16:/root/Auth2.0/resource.env.example
```

On the server, create the environment files only if they do not already exist:

```bash
test -f /root/Auth2.0/auth.env || cp /root/Auth2.0/auth.env.example /root/Auth2.0/auth.env
test -f /root/Auth2.0/resource.env || cp /root/Auth2.0/resource.env.example /root/Auth2.0/resource.env
chmod 600 /root/Auth2.0/auth.env /root/Auth2.0/resource.env
nano /root/Auth2.0/auth.env
nano /root/Auth2.0/resource.env
```

Replace **every `CHANGE_ME`** with the real database credentials and frontend
URLs. Configure mail credentials if you use OTP/email flows. URLs in `auth.env`
must use your deployed frontend, and both issuer settings must match exactly.
The frontend OAuth client ID must be `pkce-angular-auth2-client-4202`, or change
`OAUTH_CLIENT_ID` to your actual client. A previously registered client keeps its
existing callback URLs; environment changes do not update that database row.

MySQL examples assume local MySQL. Both databases must exist; `mindfullP1` needs
the existing SuperMe account schema. Back up the shared database before first
startup because Flyway runs migrations even when account writes are disabled.
This pipeline rolls back JARs, not database migrations.

If your server already has `resource.env`, change its existing `SERVER_PORT` to
`9090` before the next deployment; the pipeline preserves existing environment
files. Update the frontend resource API URL to `http://187.127.142.16:9090`
and allow port 9090 in your firewall.

Ports **9000** and **9090** must be available for these apps. If old manually
started copies or the earlier `pkce-auth`/`pkce-resource` services use those
ports, stop those copies before the first deployment. Do not stop SuperMe's
other services. Allow the ports in the server/provider firewall if needed.
HTTP URLs are initial connection settings; configure HTTPS before live logins.

## Push to deploy

Push code and the workflow to `main` or `Auth2.0`. The workflow generates temporary
test signing keys (no production keys are needed), runs tests, creates two
executable JARs, uploads a bundle, and installs/restarts these services:

- `auth2-auth`: port 9000, uses both `/root` PEM files.
- `auth2-resource`: port 9090, uses `/root/publicKey.pem`.

Both run with the `prod` profile. Keys and environment files persist across
deployments. If environment files are missing, the first run creates templates
and stops before changing services; fill them in and rerun the failed workflow.

Releases are retained under `/root/Auth2.0/releases/<run>-<attempt>`.
`/root/Auth2.0/current` points to the deployed pair of JARs. Failed startup
restores the previous release and service definitions when available. Services
start after reboot. Other repository workflows and SuperMe services are untouched.

```bash
systemctl status auth2-auth auth2-resource
journalctl -u auth2-auth -u auth2-resource -n 100 --no-pager
```
