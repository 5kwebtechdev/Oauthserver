# Back-navigation analysis and recommended standard for Super Me

Summary
- The project uses two header components: `mindful-navigator` and `mindful-card-header`.
- `mindful-navigator` already emits a `(back)` Output for parents to intercept; if no listener it dismisses modals and then calls `NavigationService.back()`.
- `mindful-card-header` exposes `backClick` Output and a `showBackArrow` input.
- A `NavigationService` records a navigation history in `sessionStorage` and provides `back()` and `backN()` helpers. This is the canonical history mechanism used across the app.

Findings (important files)
- Navigator component: src/app/core/components/mindful-navigator/mindful-navigator.component.ts
- Navigator template: src/app/core/components/mindful-navigator/mindful-navigator.component.html
- Card header: src/app/core/components/mindful-navigator/mindful-card-header/mindful-card-header.component.ts
- Navigation service: src/app/core/services/navigation.service.ts

How current back behavior works
- Default flow (no `(back)` listener):
  1. `mindful-navigator.goBack()` checks if parent bound to `(back)` — if so it emits and returns.
  2. If not, it checks for open Ionic modal and dismisses it.
  3. Finally it calls `NavigationService.back()` which uses sessionStorage-based history and falls back to `Location.back()`.
- If a page binds `(back)` or `backClick` the page fully controls behavior (can call `navigationService.back()` or do custom routing).

Common issues discovered
- Some pages call `window.history.back()` or `router.navigate(...)` directly. Those bypass the `NavigationService` history and can cause surprising back behavior elsewhere.
- Many pages reimplement `goBack()` with different return targets instead of relying on `NavigationService.back()` which fragments behavior.
- There are valid exceptions (flows that must confirm, delete, or navigate to a fixed route after an action) — these should intentionally override default, but they should do so consistently.

Recommended standardized approach
1. Default: Let `mindful-navigator` handle back (i.e., do NOT bind `(back)` on normal pages). The component will dismiss modals and call `NavigationService.back()`.
2. When you need a custom back (confirm, save/discard, special routing): bind `(back)` and implement a single small handler that either:
   - performs the special action then calls `navigationService.back()` OR
   - calls `navigationService.backN(n)` to skip entries, or `router.navigate(...)` when a fixed route is required.
3. Avoid `window.history.back()` and raw `location.href` unless absolutely necessary.

Helpful utilities / patterns (copy into a small helper file or base class)

Example: page-level handler (recommended)

```ts
// in component.ts
import { NavigationService } from 'src/app/core/services/navigation.service';

constructor(private navigation: NavigationService) {}

async handleBack() {
  if (this.hasUnsavedChanges) {
    const confirmed = await this.confirmDiscardChanges();
    if (!confirmed) return; // keep user on page
  }

  // use canonical history
  this.navigation.back();
}
```

Example: using `backN()` to skip the last page (e.g., after deleting an item)

```ts
// skip 1 previous entry and go to the one before that
this.navigation.backN(2);
```

// When handling back (e.g., via mindful-navigator (back) or mindful-card-header.backClick):

- Use approach (2) if your app is already heavily reliant on the sessionStorage history and you need to change history semantics globally.
